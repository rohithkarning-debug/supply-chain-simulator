### 3.9 Security Architecture

#### 3.9.1 Applicability of STRIDE to This System

STRIDE is normally applied to a networked, multi-user, service-hosted system with an authentication boundary, an authorisation model, network listeners and a persistent data store. The Supply Chain Management Simulator has none of those: it is a single-process Python command-line program that imports only the standard library, keeps all state in memory for the lifetime of one run, opens no sockets, stores nothing to disk and serves no requests. There is therefore no user identity to spoof, no privilege to escalate, no request to flood and no stored record to disclose during a run.

The threats that *are* real for this project are therefore of two kinds, and the security architecture addresses both:

1. **Data-integrity threats at runtime.** The simulation manipulates money-relevant quantities — stock levels, order commitments and shipment arrival days. If bad input could drive stock negative, push a warehouse past its capacity, or produce an impossible status transition, the resulting reports would be confidently wrong. This is the concern of the security objective **SCM-SO-1**, and it is enforced inside the code by validation and invariants.
2. **Supply-chain and process threats during development.** The simulator is not the only place where integrity matters. Anyone who can change the code can change what the simulator reports, and the code is developed by four people on a shared public repository. This is the concern of **SCM-SO-2**, and it is enforced by branch protection, mandatory automated verification and peer review.

Each of the six STRIDE categories is therefore analysed below against the project as built, with the threat re-cast so that it is meaningful for a local simulator and its development pipeline.

#### 3.9.2 STRIDE Analysis

| Category | Threat applicable to this system | Mitigation implemented | Related requirement IDs |
| :--- | :--- | :--- | :--- |
| **Spoofing** | At runtime there is no authentication surface: no login, no API key and no user account, so an external party cannot impersonate a caller. The equivalent threat in this project is **impersonation in the repository**. A commit attributed to someone other than its true author, or a pull request opened through an account that does not belong to the team member who wrote it, would make the change history untrustworthy and would defeat the traceability promised by SCM-SO-2. | GitHub verifies the email address behind every commit (the repository requires a GitHub-linked email in `git config user.email`), and authorship is displayed against the authenticated GitHub account rather than against free text supplied by the client. No identity is asserted at runtime because no runtime identity exists. Branch protection additionally requires that a change to `main` arrive through a pull request opened by a team member, so an anonymous contribution cannot land directly. | SCM-SO-2, SCM-SR-005 |
| **Tampering** | Two distinct tampering surfaces exist. **Runtime data tampering:** malformed input reaching a public operation and corrupting the simulation state — stock driven negative, a warehouse exceeding its capacity, an order moved through an illegal status transition, or an order silently fulfilled twice. **Codebase tampering:** a change reaching `main` that has not been reviewed or tested, including a malicious or careless dependency added to the runtime set. | *Runtime:* fail-fast validation before any mutation — `ValueError` for invalid arguments (non-positive quantity, negative lead time, reliability outside $[0,1]$, non-positive capacity, a scheduled day in the past), `InsufficientStockError` and `CapacityExceededError` for the two stock invariants, and `KeyError` for references to unknown suppliers, warehouses or orders, so that nothing is created implicitly. The overarching invariant is that **any operation which raises leaves state unchanged**. Order status transitions are guarded: a `FULFILLED` order cannot be cancelled, and `FULFILLED` and `CANCELLED` orders are never re-processed. *Codebase:* the `main` branch is protected so that no change can be pushed to it directly — a pull request is required, the required `test` check must pass, the branch must be up to date, and force pushes and deletions are blocked with the rules applied to administrators as well. Peer review by a non-author is the human control. | SCM-SO-1, SCM-SO-2, SCM-SR-001, SCM-SR-002, SCM-SR-003, SCM-SR-004, SCM-SR-005, SCM-SR-006 |
| **Repudiation** | A change that cannot be attributed to an author, or a failed check whose result is not retained, would leave the team unable to say who introduced a defect or what state the code passed CI in. Simulation state itself needs no audit trail — it is in-memory and discarded when the run ends. | Every change is traceable to a commit with a recorded author and date, and to the pull request through which it was merged, so a line of code can always be traced back to a person and a discussion. Pull requests retain their review comments and approvals as a permanent record. The GitHub Actions `test` job publishes the result of `pytest -v --cov=scm_sim` on every push to `main` and every pull request, giving a durable, dated record of which tests passed for which commit. This is the control that makes SCM-SO-2's traceability claim checkable rather than aspirational. | SCM-SO-2, SCM-SR-005, SCM-NF-003 |
| **Information disclosure** | The runtime surface for disclosure is small but must be stated: there is no data store to dump, no network egress, no log file and no credential store. The real disclosure surface is the **repository**, where a committed token, password or `.env` file would be published to every clone, and the **development machine**, where credentials would be stored insecurely. | The simulator uses only the Python standard library at runtime (`dataclasses`, `enum`, `random`, `argparse`), so it introduces no third-party code that could phone home, and it makes no network calls at all. `requirements.txt` contains only test-time dependencies (`pytest`, `pytest-cov`) and no runtime dependency is installed by an end user, so nothing needs to be trusted or fetched at run time. Secrets are kept out of the repository; repository contents are searched for tokens as part of the manual TC-SEC-02 check. Simulation data is not sensitive because it is entirely synthetic. | SCM-SR-006, SCM-NF-004 |
| **Denial of service** | There is no server to exhaust, so the realistic equivalent is **resource exhaustion inside a run**: an extreme `--days` value, an oversized quantity, or a single warehouse holding an unbounded number of tracked items could make a run consume unbounded time or memory and appear to hang. A malicious input of this kind is indistinguishable, from the operator's point of view, from a defect. | Arguments are validated at the entry point: `--days < 1` is rejected as an argparse usage error with exit code 2 before any simulation is built, so an invalid invocation fails immediately rather than looping. Within the engine, every daily loop is bounded by the number of days requested, non-positive quantities are rejected by `Inventory`, and a registered warehouse capacity bounds the stock it can hold. Performance is baselined so that a regression is detectable: a 365-day run completes in approximately 0.02 s against the 1 s budget of SCM-NF-001, measured by TC-PERF-01. There is no authentication, rate limiting or quota layer because there is no service to protect. | SCM-SR-001, SCM-NF-001 |
| **Elevation of privilege** | The project has no roles, no permissions model and no authenticated principal, so there is no runtime privilege to escalate. The equivalent threat is **bypassing the review gate on the code itself** — a team member (or anyone with repository access) merging work to `main` without review, or using an administrator account to override the protection rules. | The rules applied to `main` are enforced for administrators as well as for other users, so an administrator cannot bypass them, and force pushes and branch deletion are blocked. A pull request cannot be merged without at least one approval from someone other than its author, and the required `test` check must report success. The verification that these rules are actually in force — attempting a direct push, attempting to merge an unapproved pull request, and inspecting Settings → Branches — is defined as the manual test case TC-SEC-02, so the control is itself verified rather than assumed. | SCM-SO-2, SCM-SR-005 |

#### 3.9.4 Scope Exclusions

The following are explicitly **not** addressed, because the corresponding features do not exist in the system and their absence is a documented design decision rather than a gap. Stating them prevents a reader from reading an omission as an oversight:

- **Authentication, authorisation, session management and account roles.** The simulator has no user accounts and no login; every invocation runs with the full privileges of the operating-system user who started it.
- **Transport and network security (TLS, API security, firewalling).** The simulator opens no sockets and exchanges no data with another system, so there is nothing to encrypt or authenticate in transit.
- **At-rest encryption, key management and secure deletion.** All simulation state lives in memory for the lifetime of the process and is discarded when it exits.
- **Audit logging and tamper-evident logs.** The event record of a run is the day-by-day `DayLog` and the retained reports, which are diagnostic output rather than a security audit trail, and which disappear with the process.
- **Dependency vulnerability management and SBOM generation.** There are no runtime third-party dependencies to scan; the only dependencies are the test tools, which never execute in production.
- **Physical security and endpoint protection.** Out of scope for a source repository; these are the responsibility of the development environment.
