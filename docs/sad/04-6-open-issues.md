### 4.6 Open Issues and Next Steps

The following items are known limitations of the system as built at commit `b3702ef`, together with the improvements planned for a future iteration. They are recorded here so that the behaviour of the current release is understood as intentional and bounded rather than accidental, and so that each item has an identified owner and a target direction. None of them affects the acceptance of the requirements in SRS §8, all of which are met by the current implementation.

#### 4.6.1 Known Limitations of the Current Implementation

| # | Limitation | Affected component | Current behaviour | Impact | Owner |
| :--- | :--- | :--- | :--- | :--- | :--- |
| L1 | **One global threshold pair for all items.** Analytics classifies stock using a single `reorder_point` and a single `max_level`, while Inventory holds a `StockPolicy` per (warehouse, SKU) item. | Analytics | `find_low_stock(stock, reorder_point=20)` and `find_excess(stock, max_level=500)` apply the same thresholds to every item. A scenario in which one item is treated as high-turnover and another as bulk would have its low-stock and excess findings judged against a single pair of numbers. | Reporting accuracy only. The `Simulation` uses the same 20 / 500 defaults that `StockPolicy` applies, so a default run is self-consistent and the divergence is invisible in practice. | Pranav Achar |
| L2 | **Arrival processing aborts on a capacity breach.** If a shipment arriving today would push a warehouse past its registered capacity, `Inventory.add` raises `CapacityExceededError` and `process_arrivals` stops, leaving any remaining due shipments for that day undelivered until the next day. | Inventory / Shipment Manager | The exception propagates out of the daily arrival pass and the remaining deliveries are deferred. | The `Simulation` avoids triggering it by trimming every replenishment so that on-hand plus in-transit never exceeds capacity, so this is reachable only if the components are used directly in a way the Simulation does not permit. | Rohith Karning |
| L3 | **Order identifier consumed before validation.** `OrderManager.create` allocates the next sequential `ORD-0001` identifier before checking that the quantity is positive, so a rejected call still advances the counter. | Order Manager | After a rejected call the next successful order receives an ID one higher than a caller might expect, leaving a gap in the sequence. | Cosmetic only. The `Simulation` validates the quantity and the day before calling `create`, so the command-line path never produces a gap. | Rohanth Ganesha C |
| L4 | **New orders are served before older back-orders.** In the daily step, today's newly created orders are attempted before the oldest back-orders are retried. | Order Manager / Simulation Engine | A steady arrival of small same-day orders can postpone an older, larger back-order indefinitely. | Accepted within the stated design, which prioritises same-day service. The behaviour is deterministic and visible in the daily report, so it is reproducible and observable rather than hidden. | Rohanth Ganesha C |
| L5 | **No packaging configuration.** The project has no `pyproject.toml`, so the package is not pip-installable. | Project layout | Running the CLI requires `PYTHONPATH=src`, or a working directory of `src/`: `PYTHONPATH=src python -m scm_sim --days 10 --seed 42`. | A barrier to installation for anyone outside the repository, and the single largest contributor to the "one documented command" burden of SCM-NF-005. It does not affect any automated test, which relies on the `src` layout via `pytest.ini`. | Rohith Karning |
| L6 | **Analytics holds no history.** Each call analyses a single day. There is no notion of a previous report, so trends, average delay and time-to-resolution cannot be computed by the component itself. | Analytics | A caller that retains the reports produced by `Simulation.run(days)` can derive such figures, but Analytics offers no helper for it. | Limits reporting to "what is wrong today" rather than "how is the situation trending". | Pranav Achar |
| L7 | **Manual verification evidence outstanding.** SCM-NF-001, the reproducibility and portability halves of TC-REP-01 and TC-COV-01, and the process checks of TC-SEC-02 have not yet been executed. | Test process | These requirements carry status N in SRS §8; the code paths they cover are exercised by the automated suite, but the host-level and repository-level checks are pending. | Weakens the evidence for performance, portability and process requirements until the manual runs are completed. | Pranav Achar |

#### 4.6.2 Planned Improvements

The following improvements are the intended direction for a subsequent iteration. They are not scheduled work and are not committed deliverables; they record the thinking behind the limitations above.

| # | Planned improvement | Addresses | Sketch of the approach |
| :--- | :--- | :--- | :--- |
| P1 | **Per-item thresholds in analytics.** Replace the two global parameters with a threshold source that mirrors the `StockPolicy` values held by Inventory. | L1 | Accept an optional mapping of `(warehouse_id, sku) → policy` in `find_low_stock` and `find_excess`, falling back to the global defaults for any item not present in the mapping. This preserves the current signatures and the existing tests while allowing a per-item report. A cleaner alternative is to pass `Inventory` itself, but that would give up the dependency-free design of the component and is deliberately not preferred. |
| P2 | **Non-aborting arrival processing.** Deliver every due shipment that fits and report the ones that do not. | L2 | `process_arrivals` would accumulate a list of skipped shipments instead of propagating the first `CapacityExceededError`, logging each with its identifier and the resulting overflow so the analyst can see it in the report rather than lose the rest of the day's deliveries. |
| P3 | **Validate before allocating the order identifier.** | L3 | Move the quantity check to the top of `OrderManager.create` so a rejected call leaves the counter untouched and the sequence stays contiguous. |
| P4 | **Retry back-orders before admitting new demand.** | L4 | Reorder the daily step to place the `process_open` retry pass ahead of the creation of today's orders, which makes service strictly oldest-first. This changes the documented step order of SCM-F-041 and would require that requirement and TC-SIM-01 to be updated together. |
| P5 | **Installable package.** Add `pyproject.toml` with project metadata and a console entry point. | L5 | A minimal `pyproject.toml` declaring the project name, the Python `>= 3.11` requirement and the `src` layout would allow `pip install -e .`, giving `python -m scm_sim` and an `scm-sim` console script without any `PYTHONPATH` setting, and allowing CI to install the package rather than relying on the source tree. A build-and-publish step in the workflow would follow, which also addresses SCM-SR-006's exposure to supply-chain confusion by pinning the build tool. |
| P6 | **Trend analysis over retained reports.** | L6 | Add functions that accept a list of previously built reports and derive day-over-day deltas — days-late trend, stockout occurrences, excess exposure — so that the Simulation's retained history can be summarised without every consumer re-implementing the comparison. |
| P7 | **Data-driven scenarios.** Replace the hard-coded `build_demo` scenario with CSV or JSON input. | General usability | A scenario file describing suppliers, warehouses, policies, opening stock and scheduled orders would let an analyst explore a different network without editing Python, and would make the "configure a scenario" use case of SRS §7.1.1 testable with data rather than code. |
| P8 | **Multi-echelon networks.** Extend the topology beyond supplier → warehouse to supplier → distribution centre → store. | General scope | A second inventory tier introduces location hierarchies, transfer orders between echelons and allocation rules on fulfilment, which would replace the current single-tier fulfilment in `OrderManager`. This is a scope increase rather than a defect fix, and is listed in SRS §1.2 as out of scope for the current release. |
| P9 | **Demand forecasting and a cost model.** | General scope | Replace the scripted order schedule with a demand model, and attach a cost per unit held, ordered and shipped so that reports can quantify the cost of a stockout or of excess inventory rather than only count them. |
| P10 | **Charted or dashboarded reporting.** | General scope | Render the retained daily reports as time-series charts so trends are visible without post-processing. Because the project has no web interface by design, this would be static image or CSV output rather than an interactive dashboard, preserving the standard-library-only runtime constraint. |
| P11 | **Continuous delivery with a release package.** Extend the CI pipeline beyond the `test` job. | General process | A build job that assembles a distributable artifact on a tagged release, so that SCM-NF-003's coverage gate and the versioned releases are produced by the same pipeline that verifies them. |
