### 3.7 Risks and Mitigations

This section records the technical and process risks identified during the design of the Supply Chain Management Simulator, the likelihood and impact of each, the mitigation in place or planned, and the owner accountable for it. Likelihood and impact are rated **Low**, **Medium** or **High** on a three-point scale. Risks are derived from the architecture as built (SAD §3.3, §3.5), from the limitations recorded in SAD §4.6, and from the parallel-development and branch-protection workflow the team followed.

| # | Risk | Likelihood | Impact | Mitigation | Owner |
| :--- | :--- | :--- | :--- | :--- | :--- |
| R1 | **Integration conflict from parallel module development.** Four components were built against a fixed interface and integrated only at the end, so an interface drift between `Inventory`, `OrderManager`, `ShipmentManager` and `Simulation` would surface only at integration time. | Medium | High | Each module was specified and unit-tested against its own interface before integration, so defects surface in the owning module's test file first. `Simulation` is the single integration point and runs the complete daily sequence in a fixed order (SAD §3.5), so there is exactly one place where cross-module behaviour is exercised. Integration behaviour is covered by `tests/test_simulator.py` (TC-SIM-01, TC-SIM-02), which is mandatory on every PR. | Rohith Karning (integration) |
| R2 | **Non-deterministic output.** Unseeded or multiply-seeded randomness would make daily reports irreproducible, breaking SCM-NF-002 and making any failure impossible to re-investigate. | Low | High | One `random.Random(seed)` instance is created in `Simulation` and injected into `ShipmentManager`; no module calls the module-level `random` functions. The seed defaults to 42 and is overridable with `--seed`. Ordering inside Analytics is fully deterministic, including the `(-days_late, shipment_id)` tie-break. Enforced by `test_same_seed_gives_identical_reports` (TC-REP-01). | Pranav Achar (Analytics) / Rohith Karning (seeding) |
| R3 | **Invalid state admitted through unchecked input.** Negative stock, an over-capacity warehouse or an impossible status change would undermine SCM-SO-1 and make every downstream report meaningless. | Low | High | Fail-fast validation before any mutation: `ValueError` for invalid arguments, `InsufficientStockError` and `CapacityExceededError` for the two stock invariants, `KeyError` for unknown supplier, warehouse or order references. The invariant enforced throughout is that **any operation which raises leaves state unchanged**. Covered by TC-SEC-01 and TC-INV-01. | Rohith Karning (Inventory) / Rishi J Mule (Shipments) / Rohanth Ganesha C (Orders) |
| R4 | **Analytics thresholds diverge from inventory policy.** Analytics applies one global `reorder_point` / `max_level` pair while Inventory holds a `StockPolicy` per item, so a report can flag an item as low stock that Inventory would not reorder. | High | Medium | Accepted deliberately and documented: passing the thresholds as explicit parameters keeps Analytics free of dependencies and makes its behaviour obvious at every call site (SAD §3.4.4). The divergence is recorded as a known limitation in SAD §4.6 with per-item thresholds named as the planned improvement. Mitigated today because the `Simulation` uses the same 20 / 500 defaults that `StockPolicy` applies. | Pranav Achar (Analytics) |
| R5 | **`process_arrivals` aborts mid-pass on a capacity breach.** An arrival that would exceed warehouse capacity raises `CapacityExceededError` from `Inventory.add` and stops the remaining deliveries for that day, leaving some due shipments undelivered. | Low | Medium | The `Simulation` avoids triggering it by trimming each replenishment so that on-hand plus in-transit stock never exceeds the capacity (SCM-F-042, TC-SIM-01). The residual behaviour is documented in SAD §4.6; the planned improvement is for arrival processing to skip and report the offending shipment rather than abort the pass. | Rohith Karning (Inventory / Simulation) |
| R6 | **Back-order starvation.** Today's new orders are served before older back-orders, so a steady stream of small orders can indefinitely postpone an old large one. | Medium | Medium | Acceptable within the stated design, which prioritises same-day service; the ordering rule is deterministic, so behaviour is reproducible and visible in the daily report. Recorded in SAD §4.6 with the planned improvement of retrying back-orders before admitting new demand. | Rohanth Ganesha C (Order Manager) |
| R7 | **Order ID consumed before validation.** `OrderManager.create` allocates the next sequential `ORD-0001` identifier before checking the quantity, so a rejected call still advances the counter and leaves a gap in the sequence. | Medium | Low | The `Simulation` validates quantity and day before delegating to `create`, so the CLI path is unaffected and IDs stay contiguous in normal operation. Purely cosmetic and recorded in SAD §4.6; the planned fix is to validate before allocating. | Rohanth Ganesha C (Order Manager) |
| R8 | **Weak test evidence for process and portability requirements.** SCM-NF-004 and SCM-SR-005 cannot be verified by the pytest suite, because they concern host operating systems and GitHub branch protection rather than code. | High | Medium | The evidence is defined but not yet collected: TC-COV-01 retains a manual run on Windows 11 and Linux, and TC-SEC-02 defines the manual branch-protection and secrets checks. Both are scheduled for execution by 20-10-2026 (Test Plan §7) and are carried as status N in the RTM (SRS §8) so that the gap is visible rather than implied. CI already enforces the `test` check on every push and pull request. | Pranav Achar (Dev Lead) / Rohith Karning (CI) |
| R9 | **Unreviewed change reaches `main`.** A direct push or a self-approved pull request could merge untested or untraceable work. | Low | High | `main` is protected: a pull request is required, at least one approval from a non-author is required, the `test` check must pass, the branch must be up to date, and force pushes and branch deletion are blocked, with the rules applied to administrators as well. Changes reach `main` only through the feature-branch and pull-request flow of SAD §3.9. Verified manually by TC-SEC-02. | Rohith Karning (repository owner) |
| R10 | **Single-owner knowledge concentration.** Each module is owned by one team member, so a module becomes hard to maintain if that member is unavailable, and a defect in an unfamiliar module is slow to diagnose. | Medium | Medium | Mitigated by the fixed, narrow interface of each component and by the API documentation in SAD §4.3, which lets any member call a component without reading its source. The layered architecture in SAD §3.5 confines a change to one module in most cases, so cross-module impact is limited. Residual exposure is accepted for a four-person semester project. | Team (all members) |
| R11 | **Runaway runtime on large inputs.** A very large `--days` value or an oversized quantity could make a run take unbounded time or memory. | Low | Medium | Arguments are validated at the CLI (`--days < 1` is a usage error, exit code 2) and every daily loop is bounded by the number of days requested. `Inventory` rejects non-positive quantities and enforces registered capacities. Performance is baselined by TC-PERF-01: a 365-day run completes in roughly 0.02 s against a 1 s budget (SCM-NF-001). | Rohith Karning (CLI / Simulation) |
| R12 | **Secrets or runtime third-party dependencies enter the repository.** A committed token or a runtime library would violate SCM-SR-006 and widen the attack surface. | Low | Medium | The simulator imports only the standard library at runtime (`dataclasses`, `enum`, `random`, `argparse`) and makes no network calls; `requirements.txt` holds test-only dependencies (`pytest`, `pytest-cov`). The repository is searched for tokens as part of the manual TC-SEC-02 check. | Rishi J Mule (Security Test Engineer) |
| R13 | **Documentation drifts from the implementation.** Requirements, design and tests are written after the code, so a later change can leave a documented behaviour that no longer holds. | Medium | Medium | Every requirement, component and test case in these documents names the concrete function, exception and pytest test that implements it, so drift is visible when the named test fails to cover the documented behaviour. Changes reach `main` only after the `test` check passes, and the Requirements Registry is the single source of truth for all IDs, so any divergence must be reconciled against it rather than invented locally. | Team (all members) |

#### 3.7.1 Residual Risk Summary
R1, R2, R3, R5, R6, R7, R9, R11 and R12 are all mitigated with controls that are in place today and are covered by passing automated tests. The remaining exposure is concentrated in three places: **R4** and **R10**, which are accepted consequences of the chosen architecture and team size rather than defects; **R13**, which is mitigated by process rather than eliminated; and **R8**, the only risk whose mitigation is scheduled but not yet complete, since the six requirements carried at status N in SRS §8 — SCM-NF-001, SCM-NF-002, SCM-NF-003, SCM-NF-004, SCM-SR-005 and SCM-SR-006 — await manual execution on 20-10-2026. No risk is assessed as High likelihood with unmitigated High impact.
