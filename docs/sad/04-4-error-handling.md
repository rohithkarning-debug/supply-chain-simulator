### 4.4 Error Handling and Logging

#### Architectural Invariant: Fail Fast, Leave State Unchanged
The Supply Chain Management Simulator enforces a strict state-integrity invariant across all subsystems: **any operation that raises an exception fails immediately and leaves internal simulation state completely unchanged**.

No partial updates, corrupted records, or dangling references are permitted. If an operation fails during validation or domain constraint enforcement, the system guarantees that all in-memory collections, inventory levels, order books, and shipment logs remain identical to their pre-invocation state.

#### System Exceptions Reference Table

The following table details all exceptions utilized within the simulator, their triggering conditions, and their state-preservation guarantees:

| Exception Class | Module Origin | Trigger Condition | State Guarantee |
| :--- | :--- | :--- | :--- |
| **`ValueError`** | Built-in | - Quantity `<= 0` in orders or shipments.<br>- Supplier `lead_time_days < 0`.<br>- Supplier `reliability` not in `[0.0, 1.0]`.<br>- Duplicate `supplier_id` registration.<br>- Warehouse `capacity <= 0`.<br>- Negative `StockPolicy` parameters or `max_level < reorder_point`.<br>- Scheduled order day `<= current_day`.<br>- Attempting to cancel an order with status `FULFILLED`.<br>- CLI invocation with `--days < 1`. | Method exits immediately before instantiating or inserting entities. Existing inventory, orders, and suppliers remain unchanged. |
| **`KeyError`** | Built-in | - Referencing an unknown `supplier_id` in `dispatch()` or `set_policy()`.<br>- Referencing an unknown `warehouse_id` in `schedule_order()` or `add_stock()`.<br>- Referencing a non-existent `order_id` in `get()` or `cancel()`. | No entity is created implicitly; lookup fails and dictionaries remain untouched. |
| **`InsufficientStockError`** | `scm_sim.inventory` | Calling `Inventory.remove(warehouse, sku, qty)` when `qty > level(warehouse, sku)`. | Stock level is left completely unchanged; no partial deduction occurs. |
| **`CapacityExceededError`** | `scm_sim.inventory` | Calling `Inventory.add(warehouse, sku, qty)` when adding `qty` would push total warehouse units over registered capacity. | Stock level is left completely unchanged; excess goods are rejected. |
| **CLI Usage Error** | `argparse` | Invoking the command-line interface with invalid arguments, unrecognizable flags, or non-integer values. | CLI catches the parsing error, prints standard usage text to `stderr`, and terminates with exit code 2 without starting simulation. |

#### Error Handling Strategies across Subsystems

1. **Input and Parameter Validation:**
   - Dataclass `__post_init__` hooks (`Supplier`, `StockPolicy`, `Order`, `Shipment`) validate structural invariants at construction time.
   - Public manager methods (`OrderManager.create`, `ShipmentManager.dispatch`, `Simulation.schedule_order`) validate relational parameters before state insertion.

2. **Domain Exception Hierarchy:**
   - Custom exceptions (`InsufficientStockError`, `CapacityExceededError`) inherit from `Exception`, allowing domain callers to distinguish operational business rule rejections from systemic programming errors.

3. **Status Guarding:**
   - Order fulfillment and cancellation operations guard against invalid state regressions:
     - Orders with status `FULFILLED` cannot be cancelled (raises `ValueError`).
     - Orders with status `FULFILLED` or `CANCELLED` cannot be re-processed (returns `False` safely without raising).

#### Logging and Observability

Because the simulator operates as an isolated in-memory Python application without external logging daemons or network sinks, observability is provided through three structured mechanisms:

1. **Structured Daily Event Logging (`DayLog`):**
   - Each simulation step creates a `DayLog` instance capturing the events of that day:
     - Arriving shipments received into inventory.
     - Customer orders created and fulfilled today.
     - Back-orders newly fulfilled during retry passes.
     - Replenishment orders dispatched to suppliers.
   - The simulation maintains a complete historical list of daily logs accessible via `Simulation.history`.

2. **Console Streaming:**
   - When executed via the CLI (`python -m scm_sim`), the runner prints a formatted execution log line for each day to `stdout`:
     ```text
     Day 1: arrivals=0, orders=2, fulfilled=2, backordered=0, replenished=1
     ```
   - On completion, the CLI prints a clean, multi-line formatted summary report generated by `analytics.format_report()`.

3. **Continuous Integration Test Logging:**
   - Automated test execution through GitHub Actions captures detailed step-by-step logs for all 73 test cases with `-v` (verbose) flags and statement-by-statement coverage breakdowns via `pytest-cov`.
