### 5.1 Security Validation

As established by the Security Test Engineer (Rishi J Mule), security and data integrity testing validates that the simulator resists invalid inputs, prevents ledger corruption, and enforces development governance standards as specified in SRS §5.1 (SCM-SO-1, SCM-SO-2, SCM-SR-001 through SCM-SR-007).

#### Security Test Checks and Verification Matrix

The security validation suite verifies eight core security controls across all domain modules:

| Security Control ID | Target Invariant / Boundary | Threat Mitigated | Test Verification Strategy | Automated By |
| :--- | :--- | :--- | :--- | :--- |
| **SEC-VAL-01: Public Parameter Validation** | All public API operations reject non-positive quantities (`qty <= 0`), negative lead times (`lead_time < 0`), invalid reliability metrics (`reliability not in [0.0, 1.0]`), invalid policies, and capacity `<= 0` with `ValueError`. | Data corruption and arithmetic anomalies from malformed inputs. | Parameterized boundary tests asserting `pytest.raises(ValueError)` before state changes. | `tests/test_inventory.py`<br>`tests/test_orders.py`<br>`tests/test_shipments.py`<br>`tests/test_simulator.py` |
| **SEC-VAL-02: Non-Negative Stock Invariant** | Warehouse inventory balance can never drop below zero. Attempting to remove more stock than on hand raises `InsufficientStockError` and leaves stock unchanged. | Inventory balance spoofing and phantom deficits. | Negative boundary test asserting `InsufficientStockError` raised when `qty > level(wh, sku)`. | `test_inventory.py::test_remove_too_much_raises` |
| **SEC-VAL-03: Storage Capacity Ceiling Invariant** | Total inventory across all SKUs in a registered warehouse can never exceed registered capacity. Breaches raise `CapacityExceededError` and leave stock unchanged. | Storage overflow and unbounded memory consumption. | Boundary tests asserting `CapacityExceededError` when `total + qty > capacity`. | `test_inventory.py::test_add_beyond_capacity_raises_and_leaves_stock_unchanged` |
| **SEC-VAL-04: Guarded Order Lifecycle** | Orders in status `FULFILLED` cannot be cancelled; orders in status `FULFILLED` or `CANCELLED` cannot be re-processed or double-credited. | Double-spending, illegitimate order modifications, and inventory ledger desynchronization. | Negative lifecycle tests attempting cancellation and fulfillment on finalized orders. | `test_orders.py::test_cancel_rules`<br>`test_orders.py::test_fulfil_enough_stock` |
| **SEC-VAL-05: Strict Entity Lookup (No Implicit Creation)** | Referencing an unregistered supplier, warehouse, or order ID immediately raises `KeyError` without generating phantom objects. | Unvetted entity injection and state hijacking. | Negative lookup tests querying non-existent keys across managers. | `test_shipments.py::test_add_supplier_and_reject_duplicate_and_unknown`<br>`test_orders.py::test_cancel_rules` |
| **SEC-VAL-06: State Immutability via Snapshots** | Data returned to external callers (such as `Inventory.snapshot()`) must be deep/independent copies. | External state tampering and memory leakage across module boundaries. | Snapshot mutation test asserting that altering the returned dictionary leaves internal `_stock` unchanged. | `test_inventory.py::test_snapshot_returns_independent_copy` |
| **SEC-VAL-07: Branch Protection Enforcement** | `main` branch must enforce code reviews, passing CI status checks, linear history, and block direct pushes and force pushes. | Unauthorized, unreviewed, or broken code reaching the production branch. | Manual process audit attempting direct push and unapproved PR merge (TC-SEC-02). | GitHub repository branch ruleset audit |
| **SEC-VAL-08: Dependency & Credential Isolation** | Repository contains zero secrets, tokens, or credentials; application makes zero runtime network calls and depends strictly on the standard library. | Supply chain attacks, credential leakage, and runtime remote code execution. | Static code scan for credentials; audit of `requirements.txt` to verify test-only dependencies. | Static analysis and dependency audit (TC-SEC-02) |
