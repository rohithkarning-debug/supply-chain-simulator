### TC-INV-02: Stock Policies, Reorder Suggestions and Snapshots

| Field | Content |
|---|---|
| TC ID | TC-INV-02 |
| Title | Validate stock policies, detect reorder and excess at their boundaries, list reorder suggestions in order, and return independent snapshots |
| Requirement(s) | SCM-F-003, SCM-F-004 (also supports SCM-SR-001, SCM-SR-007) |
| Type | Functional (unit, boundary-value) |
| Preconditions | 1. Python 3.11 virtual environment with `pip install -r requirements.txt` completed. 2. Repository at commit `b3702ef` (or a later green `main`). 3. Each step starts from a new, empty `Inventory()`; `StockPolicy` imported from `scm_sim.inventory`. |
| Test data | Made-up IDs as used in the test code: warehouses `WH1`, `WH2`, `WH3`; SKUs `SKU1`, `SKU2`, `SKU3`, `SKU9`. Invalid policies: `reorder_point=-1`, `reorder_quantity=-1`, `max_level=-1`, and `reorder_point=50, max_level=49`. Boundary levels: 21 → 20 for reorder point 20; 100 → 101 for max level 100. |
| Objective | Prove that invalid policies are rejected, that reorder and excess decisions switch exactly at their thresholds, that reorder suggestions include every tracked item that needs one in a fixed sorted order, and that a snapshot cannot be used to change stock. |
| Steps | 1. Create `StockPolicy(**kwargs)` for each of the four invalid parameter sets. 2. Set `StockPolicy(reorder_point=20)` on (`WH1`, `SKU1`), add 21 units and call `needs_reorder`; remove 1 unit and call `needs_reorder` again. 3. Set `StockPolicy(reorder_point=0, max_level=100)` on (`WH1`, `SKU1`), add 100 units and call `is_excess`; add 1 more and call `is_excess` again. 4. Add 5 × (`WH2`, `SKU1`), 300 × (`WH1`, `SKU9`), 10 × (`WH1`, `SKU2`) then remove those 10, and set `StockPolicy(reorder_quantity=40)` on (`WH1`, `SKU1`) without stock; call `reorder_suggestions()`. 5. Add 10 × (`WH1`, `SKU1`) and 5 × (`WH2`, `SKU2`); take `snapshot()`; set its (`WH1`, `SKU1`) entry to 999 and add a key (`WH3`, `SKU3`); read `level` and take a new `snapshot()`. |
| Expected result | 1. Each of the four raises `ValueError`. 2. `False` at 21, `True` at 20 (the reorder point itself triggers a reorder). 3. `False` at 100, `True` at 101 (only levels above max level are excess). 4. Exactly `[("WH1", "SKU1", 40), ("WH1", "SKU2", 100), ("WH2", "SKU1", 100)]`: the policy-only item and the sold-out item are included, the healthy `SKU9` is not, and the list is sorted by warehouse then SKU. 5. The first snapshot equals `{("WH1", "SKU1"): 10, ("WH2", "SKU2"): 5}`; after editing it, `level("WH1", "SKU1") == 10`, `level("WH3", "SKU3") == 0`, and a new snapshot still equals the original values. |
| Pass/fail criteria | **Pass** if every step gives exactly the expected result and all pytest tests listed below pass. **Fail** if an invalid policy is accepted, a boundary decision is off by one, the suggestion list differs in content or order, or editing a snapshot changes the inventory. |
| Automated by | `tests/test_inventory.py::test_stock_policy_rejects_invalid_values` (4 parametrised cases), `tests/test_inventory.py::test_needs_reorder_at_boundary`, `tests/test_inventory.py::test_is_excess_only_above_max_level`, `tests/test_inventory.py::test_reorder_suggestions_sorted_and_only_tracked_items`, `tests/test_inventory.py::test_snapshot_returns_independent_copy`. Supporting: `test_stock_policy_defaults` (20 / 100 / 500), `test_stock_policy_allows_max_level_equal_to_reorder_point`, `test_get_policy_returns_default_when_unset`, `test_set_policy_is_per_warehouse_and_sku`, `test_reorder_suggestions_empty_for_new_inventory` |
