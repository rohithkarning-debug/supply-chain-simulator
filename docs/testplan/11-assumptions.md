### 11. Assumptions and Dependencies

#### 11.1 Assumptions

The test effort defined in this plan rests on the assumptions below. Each is stated so that a reviewer can judge whether the plan is still valid if the assumption fails, and so that a failure of an assumption is not mistaken for a defect in the system under test.

| # | Assumption | Basis | Consequence if it does not hold |
| :--- | :--- | :--- | :--- |
| A1 | **The source code under test is the version merged into `main` at commit `b3702ef`.** All test items, interfaces and baselines in §2 refer to this commit. | The code is built and merged; `main` is at `ef435c7` with this baseline among its history. | Any change after the baseline invalidates the affected interface listing in §2.4 and requires the affected test cases to be re-executed before the results are reported. |
| A2 | **One supplier serves each item, and demand is known in advance.** A scenario links one supplier to each per-item policy, and orders are scheduled for explicit future days. | SRS §2.6 states these as design assumptions of the simulated network. | If multi-sourcing or demand uncertainty were introduced, SCM-F-042 and SCM-F-012 would need to specify a selection rule that does not currently exist, and TC-SIM-01 would no longer be sufficient for them. |
| A3 | **Delays only ever make a shipment later.** The delay model adds 1–3 days to the arrival day and never brings it forward. | SCM-F-022 defines the model as an addition only; `rng.random() > reliability` yields 0 or a positive delay. | Early-arrival cases would need their own analytics behaviour. `find_delayed_shipments` would still exclude them (`days_late > 0`), so TC-ANA-01 would remain valid, but the days-late semantics documented in SAD §4.3.4 would need revision. |
| A4 | **Randomness is drawn from a single injected `random.Random(seed)`.** No module calls the module-level `random` functions. | SAD §3.6; the PRNG is created once in `Simulation` and injected into `ShipmentManager`. | SCM-NF-002 becomes unverifiable, because no run would be reproducible. This assumption is directly tested by `test_same_seed_gives_identical_reports` in TC-REP-01, so a violation would be detected rather than assumed away. |
| A5 | **The Python runtime is version 3.11 or later and provides the standard-library modules the system uses.** The system imports only `dataclasses`, `enum`, `random` and `argparse` at runtime. | SRS §2.4, §5 (SCM-NF-004); `requirements.txt`. | Test results from one interpreter version do not transfer to another. This is why the portability half of TC-COV-01 is executed on a second host rather than inferred from CI. |
| A6 | **The CI environment is representative enough to execute the automated suite.** GitHub Actions `ubuntu-latest` with Python 3.11 runs `pytest -v --cov=scm_sim` and its result is treated as the platform-neutral result. | SCM-NF-003, SCM-NF-004; the workflow in `.github/workflows/ci.yml`. | A failure specific to a platform CI does not cover, such as Windows path or line-ending behaviour, would go undetected. This is the gap the manual portability run in TC-COV-01 exists to close. |
| A7 | **All test data is synthetic.** Every identifier used in a test case — warehouses `WH-NORTH`, `WH-SOUTH`, SKUs `WIDGET`, `GADGET`, `GIZMO`, customers `C-ACME`, suppliers `SUP-RELIABLE`, `SUP-FLAKY`, orders `ORD-0001`, shipments `SHP-0001` — is invented for the purpose. | No real supply chain, customer or supplier data exists in the project, and none is required. | If real data were introduced, SCM-SR-006 would need review, because the repository is assumed to hold no confidential material. The assumption is verified by the secrets scan in TC-SEC-02. |
| A8 | **GitHub branch protection is configured as specified.** The rules for `main` are those enumerated in SCM-SR-005. | The team's documented workflow; the rules are not visible in the repository itself. | TC-SEC-02 must inspect Settings → Branches rather than trust this assumption, which is why it is defined as a manual check rather than an automated one. |
| A9 | **A performance measurement on a standard development laptop is representative.** The reference platform is an ordinary x86-64 laptop rather than a constrained or server-grade machine. | SCM-NF-001 specifies a "standard laptop with Python 3.11" and records baselines of roughly 0.02 s and 0.10 s. | If a slower or faster host is used, the measured time must be reported together with the host description, and the 1 s budget evaluated against that context. |
| A10 | **The requirements registry is stable and correct.** The IDs in `docs/requirements-registry.md` match SRS, SAD and this plan, and no requirement ID is changed or added without notifying the repository owner. | The registry is the single source of truth agreed by the team. | Every traceability table in all three documents would need re-derivation. Changes to IDs are therefore treated as a document-level event rather than an editing convenience. |

#### 11.2 Dependencies

The test effort cannot be completed independently of the following. Each dependency states what is required, who provides it and what happens if it is unavailable.

| # | Dependency | Provided by | Needed for | Effect if unavailable |
| :--- | :--- | :--- | :--- | :--- |
| D1 | **A working Python 3.11 environment** with `pytest` and `pytest-cov` installed from `requirements.txt`. | Each team member; CI provisions it automatically. | Execution of every automated test case. | Automated execution stops. Results already recorded for commit `b3702ef` remain valid for that commit only. |
| D2 | **The `test` CI job on GitHub Actions** (`ubuntu-latest`, Python 3.11, `pytest -v --cov=scm_sim`). | Repository owner (Rohith Karning). | Continuous regression testing of every pull request; the SCM-NF-003 coverage gate; the SCM-SR-005 merge condition. | No merge is permitted, because the required check cannot be satisfied. Testing becomes manual-only, which is not an acceptable fallback for this project. |
| D3 | **GitHub branch protection on `main`.** | Repository owner (Rohith Karning), configured in repository settings. | SCM-SR-005; TC-SEC-02. | The merge gate is unenforced. SCM-SR-005 would fail and, with it, the integrity objective SCM-SO-2. |
| D4 | **A second, non-CI host running Windows** for the portability execution. | A team member with a Windows 11 laptop (see Test Plan §6). | The manual half of TC-COV-01 covering SCM-NF-004. | SCM-NF-004 stays at status N. Portability would be evidenced for Linux only, which is insufficient to claim support for Windows and macOS. |
| D5 | **Wall-clock timing capability** (`time` on bash, `Measure-Command` in PowerShell) and three consecutive runs per measurement. | Standard on both host operating systems; no purchase required. | TC-PERF-01 covering SCM-NF-001. | Performance cannot be evidenced. A single run would not distinguish a genuine pass from timing noise, so the three-run requirement is retained. |
| D6 | **The test suite itself.** 73 automated tests across `tests/test_analytics.py`, `test_inventory.py`, `test_orders.py`, `test_shipments.py` and `test_simulator.py`. | All four team members, one owner per module. | Every automated test case in §13. | A test case whose automation is missing or failing cannot be reported as passed, regardless of whether manual reasoning suggests the behaviour is correct. |
| D7 | **The requirements registry and the three specifications** (SRS v1.0, SAD v1.0, this Test Plan v1.0). | Product Owner (Rohith Karning) as owner of the registry. | Traceability in §13, the feature list in §3 and the status column of SRS §8. | Traceability cannot be asserted, and the exit criteria in §5.4 — which require every planned test case to have been executed against a named requirement — cannot be evaluated. |
| D8 | **Access to repository settings** for the branch-protection and secrets inspection. | Repository owner. | The manual steps of TC-SEC-02. | SCM-SR-005 and SCM-SR-006 cannot be evidenced by inspection and remain unverified. |
| D9 | **Documentation of the single demo command** (`PYTHONPATH=src python -m scm_sim --days 10 --seed 42`). | README of the repository. | The usability half of SCM-NF-005, exercised in TC-SIM-02. | A new user cannot run the demo unaided, so SCM-NF-005 fails even though the CLI itself behaves correctly. |
| D10 | **Team availability for peer review and for the remaining manual executions**, scheduled to complete by 20-10-2026 (Test Plan §7). | All four team members. | Reviewer rotation, and the six requirements still at status N in SRS §8. | Those requirements remain unverified and the project cannot report full acceptance, even though no code defect is implied. |

#### 11.3 Assumptions and Dependencies Not Applicable

Two categories that would normally appear in this section do not apply to this project, and are recorded here so that their absence is deliberate:

- **No test data management dependency.** There is no database, no production dataset and no data-masking process. All test data is constructed in code by `build_demo()` or by small in-test fixtures, and is entirely synthetic.
- **No external service or network dependency.** The simulator makes no network calls and depends on no external service, API or database at test time, so there is nothing to stub, mock or rate-limit, and no third-party outage can affect test execution.
